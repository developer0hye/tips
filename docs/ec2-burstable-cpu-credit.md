# EC2 T 시리즈의 unlimited 모드가 청구서를 터뜨린다

AWS에서 가장 흔하게 쓰이는 `t3.micro`는 **burstable 인스턴스**다. 상시 성능을 보장하는 대신 평소엔 적게 쓰고 필요할 때 잠깐 몰아 쓰는 구조다. 문제는 "잠깐"이 "한 달 내내"가 됐을 때 어떻게 되는지를 대부분 모른 채로 쓴다는 점이다.

실제로 겪었다. 평소 $14 나오던 계정이 **한 달에 $101**이 나왔고, 그중 **$61.62가 CPU 크레딧 초과분** 한 항목이었다.

## 어떻게 돌아가는가

T 시리즈는 휴대폰 데이터 요금제와 구조가 같다.

- **기본 제공량**: 인스턴스마다 baseline CPU 사용률이 정해져 있다. `t3.micro`는 10%다.
- **적립금**: baseline보다 적게 쓰면 CPU 크레딧이 쌓인다. 많이 쓰면 쌓아둔 크레딧을 깎아서 쓴다.
- **적립금이 바닥나면**: 여기서 두 갈래로 갈린다. 그리고 이 갈림길이 요금의 전부다.

| 모드 | 크레딧 소진 후 동작 | 추가 요금 |
|---|---|---|
| `unlimited` | 계속 baseline 이상으로 동작 | **시간당 과금, 상한 없음** |
| `standard` | baseline까지 성능이 제한됨 | **$0** |

**`unlimited`이 기본값이다.** 콘솔에서 인스턴스를 만들 때 이 항목을 명시적으로 건드린 기억이 없다면, 지금 `unlimited`으로 돌고 있다고 보면 된다.

## 실제로 터진 사례

프로필 사이트를 올려둔 `t3.micro` 한 대에서 벌어진 일이다.

```
CPU 사용률 (하루 평균)
6/18 ~ 6/25   0.3%   ← 정상. 정적 사이트 + 작은 API 서버
6/26          53%    ← 무언가 시작됨
6/27 ~ 8/02   92~96% ← 37일간 24시간 내내
```

원인이 무엇이든(침해든 폭주한 프로세스든) **비용 관점에서 중요한 건 그 다음이다.**

```
7월 청구서 $101.06
├─ CPU 크레딧 초과분   $61.62   ← 1,232 vCPU-hour × $0.05
├─ EC2 컴퓨팅          $19.34   ← 프리티어가 마침 같은 주에 만료
├─ 세금                 $9.18
├─ 공인 IP (2개)        $7.44
└─ EBS 디스크           $3.47
```

`standard` 모드였다면 이 인스턴스는 baseline인 10%로 스로틀링됐을 것이고, **초과분 $61.62는 $0이었다.** 사이트가 느려지는 걸 보고 하루 안에 알아챘을 것이다. 대신 한 달을 모르고 지나갔다.

### 왜 늦게 알았나

`unlimited` 모드의 진짜 위험은 금액이 아니라 **증상이 없다는 것**이다.

- 서버는 정상적으로 응답한다. 모니터링 알람도 안 울린다.
- CPU가 100%든 1%든 사용자 경험이 똑같다. AWS가 알아서 성능을 채워주기 때문이다.
- 그래서 **청구서가 도착할 때까지 아무도 모른다.** 그때는 이미 한 달치가 확정된 뒤다.

성능 저하는 즉시 눈에 보이는 신호지만, 초과 과금은 30일 뒤에 오는 신호다. `standard`는 이 신호를 앞당겨준다.

## 확인과 변경

**지금 어느 모드인지 확인:**

```bash
aws ec2 describe-instance-credit-specifications \
  --region <리전> --instance-ids <인스턴스ID> \
  --query 'InstanceCreditSpecifications[0].CpuCredits' --output text
```

**`standard`로 변경:**

```bash
aws ec2 modify-instance-credit-specification \
  --region <리전> \
  --instance-credit-specification InstanceId=<인스턴스ID>,CpuCredits=standard
```

인스턴스가 실행 중이든 정지 상태든 즉시 적용되고, 재부팅이 필요 없다.

**과거에 초과분을 낸 적이 있는지 확인:**

```bash
aws ce get-cost-and-usage \
  --time-period Start=2026-01-01,End=2026-08-01 \
  --granularity MONTHLY --metrics UnblendedCost \
  --group-by Type=DIMENSION,Key=USAGE_TYPE
```

`CPUCredits:t3` 항목이 보이면 이미 내고 있는 것이다. Cost Explorer API는 요청당 $0.01이 과금되니 필요한 만큼만 호출한다.

## 트레이드오프

`standard`가 항상 정답은 아니다.

- **적합한 경우**: 개인 사이트, 블로그, 사내 도구처럼 평소 CPU를 거의 안 쓰는 서버. baseline에 걸릴 일이 없으니 잃는 게 없고, 이상 상황일 때만 스로틀링이 걸려 오히려 조기 경보가 된다.
- **주의할 경우**: 배포할 때마다 빌드를 서버에서 돌리는 구조라면 빌드가 느려진다. 이때는 빌드 직전에만 `unlimited`으로 바꿨다가 되돌리거나, 빌드를 CI로 옮기고 서버는 산출물만 받게 하는 편이 낫다.
- **트래픽이 실제로 튀는 서비스**라면 `unlimited`을 유지하되 **반드시 일일 예산 알림을 건다.** 모드 선택을 안 할 거면 감시라도 해야 한다.

## 같이 걸어둘 것

모드만 바꾸면 이 실패 하나는 막지만, 다음 실패는 다른 얼굴로 온다.

1. **일일 예산 알림** — 월 예산은 늦다. 이번 건도 하루 $2씩 32일에 걸쳐 쌓였다. 월 예산 80% 알림은 3주 뒤에나 울린다. 하루 단위로 걸어야 이틀 만에 안다.
2. **CloudWatch CPU 알람** — 평균 CPU가 baseline을 크게 넘긴 상태가 지속되면 알림. 비용 신호보다 빠르다.
3. **Cost Anomaly Detection** — 무료다. 총액이 예산 안이어도 특정 항목이 튀면 잡아준다.
4. **프리티어 만료일을 캘린더에 적어둔다** — 계정 생성 12개월 뒤다. 이번에도 CPU 폭주와 프리티어 만료가 같은 주에 겹쳐서 원인 분석이 한 겹 더 꼬였다. 만료 자체는 사고가 아니지만, 사고와 겹치면 판단을 흐린다.

## 한 줄 요약

> T 시리즈의 `unlimited`은 성능 저하를 요금으로 바꿔주는 옵션이다. 개인 서버라면 `standard`로 두자 — 느려지는 건 눈에 보이지만, 초과 과금은 30일 뒤 청구서로만 보인다.
