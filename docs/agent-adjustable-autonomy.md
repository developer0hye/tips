# 에이전트의 자율성은 스위치가 아니라 다이얼이어야 한다 — 수동 제어에서 완전 자율까지

Agent 제품이 실패하는 방식은 두 가지다.

- **너무 물어본다.** 파일 하나 읽을 때마다 승인을 요구한다. 사용자는 세 번째 요청부터 읽지 않고 Enter를 친다. 승인은 형식이 되고, 결국 "그냥 다 허용" 모드로 도망간다
- **너무 안 물어본다.** 시키는 대로 끝까지 한다. 어느 날 production DB의 테이블을 지우고 나서야 "확인을 했어야 했다"는 걸 안다

둘의 공통 원인은 **자율성이 on/off 스위치**라는 것이다. "매번 확인" 아니면 "전부 자동". 그 사이가 없으니 사용자는 둘 중 덜 나쁜 쪽을 고르고, 둘 다 나쁘다.

효과적인 agent 시스템은 자율성을 **다이얼**로 제공한다. 완전 수동 제어에서 완전 자율 운영까지, 사용자가 **작업마다, 행동 종류마다, 시간에 따라** 위치를 옮길 수 있어야 한다. 그리고 그 이동이 **부드러워야** 한다. 설정 파일을 뜯거나 코드를 고치는 게 아니라, 한 번의 선택으로.

> 이 문서는 [5가지 원칙](agentic-system-principles.md)의 Resilience에서 다룬 approval gate와 [핵심 구성요소](agent-core-components.md)의 Orchestration을 "누가 얼마나 결정하나"라는 축에서 다시 본다.

## 1. 자율성의 단계

자율주행의 레벨 구분을 빌리면 다섯 단계로 나눌 수 있다.

| Level | 이름 | 누가 결정하나 | 사용자의 역할 | 예 |
|---|---|---|---|---|
| **L0** | Manual | 사용자 | 직접 실행. Agent는 제안만 | 자동완성, "이 명령을 실행하시겠어요?" |
| **L1** | Approve each action | Agent가 제안, 사용자가 매번 승인 | 매 step의 검문소 | 모든 tool 호출 전 확인 |
| **L2** | Approve by policy | 정책이 결정. 읽기는 자동, 쓰기는 승인 | 정책을 정하고 예외만 승인 | "파일 읽기는 허용, 삭제는 물어봐" |
| **L3** | Supervised autonomy | Agent가 끝까지 수행. 사용자는 관찰하고 개입 가능 | 결과 검토, 필요시 중단 | 경계 안에서 자동 실행, 완료 후 diff 검토 |
| **L4** | Full autonomy | Agent. 사람은 사후 감사 | 없음 (감사만) | 스케줄된 무인 작업, CI bot |

레벨이 올라갈수록 **사용자가 개입하는 시점이 뒤로 밀린다.** L1은 행동 전에, L3는 행동 중이나 후에, L4는 한참 뒤 감사 때 개입한다. 뒤로 밀린 만큼 사고의 영향 범위가 커지므로, 레벨을 올릴 때는 다른 것으로 보상해야 한다(4절).

**어느 레벨이 정답인가?** 정답은 없다. 같은 사용자도 작업마다 다르다.

| 작업 | 적절한 레벨 | 이유 |
|---|---|---|
| 로그 조회, 코드 검색 | L3–L4 | 읽기만 하고, 틀려도 되돌릴 게 없다 |
| 코드 수정 (git 안에서) | L2–L3 | 되돌릴 수 있다. diff로 사후 검토 가능 |
| DB migration | L1 | 되돌리기 어렵고 영향이 넓다 |
| 결제, 외부 발송 | L0–L1 | 되돌릴 수 없고, 제3자에게 영향 |

**같은 작업도 시간에 따라 다르다.** 처음 쓰는 agent에게 L3를 주는 사용자는 없다. 열 번 지켜보고 괜찮으면 올린다. 사고가 나면 내린다. 이 곡선을 시스템이 지원해야 한다.

## 2. "부드럽게"가 뜻하는 것

다이얼이 있다는 것과 다이얼이 부드럽다는 것은 다르다. 부드러움의 조건은 다섯 가지다.

### 연속적이다

단계 사이 이동에 코드 수정이나 재배포가 필요하면 다이얼이 아니다. 설정 한 줄, 클릭 한 번, 혹은 대화 중 한 문장("이제부터 테스트 파일은 그냥 고쳐")으로 옮겨져야 한다.

### 다차원이다

자율성은 숫자 하나가 아니다. 최소 네 축이 독립적으로 움직인다.

| 축 | 예 |
|---|---|
| **행동 종류** | 읽기 자동 / 쓰기 승인 / 삭제 금지 |
| **범위** | 이 디렉터리 안은 자유, 밖은 물어봐 |
| **자원** | 이 세션은 비용 $5까지, step 50까지 |
| **시간·맥락** | 근무 시간엔 L3, 야간 무인 실행은 L2 |

"L3 모드"라는 하나의 스위치는 이 축들을 한 값으로 묶어버린다. 사용자가 원하는 건 "코드 수정은 자유롭게, 하지만 `git push`는 물어봐"처럼 축마다 다른 위치다.

### 양방향이다

올리는 것보다 **내리는 것이 더 쉬워야 한다.** 사고가 나고 있을 때 "설정 화면으로 가서..."는 늦다. 실행 중 즉시 멈추기(stop), 잠시 멈추기(pause), 방금 한 것 되돌리기(rollback)가 한 동작이어야 한다.

### Agent 자신도 다이얼을 내릴 수 있다

사용자가 L3로 놓았어도, agent가 확신이 없거나 지시가 모호하거나 예상 밖의 상황을 만나면 **스스로 L1로 내려와 물어봐야 한다.** "삭제하라고 하셨는데 파일이 300개입니다. 계속할까요?" 이것이 없으면 L3는 "지시가 모호할 때 추측해서 실행하는 모드"가 된다.

반대로 agent가 스스로 다이얼을 **올리는** 것은 허용하지 않는다. 자율성 확대는 사람만 결정한다.

### 기본값은 보수적이다

처음 만나는 사용자, 처음 보는 작업, 처음 쓰는 tool은 낮은 레벨에서 시작한다. 올리는 것은 사용자의 명시적 선택이다. 반대로 하면(기본 L3, 원하면 낮추기) 사고가 먼저 나고 설정이 나중에 온다.

## 3. 설계 메커니즘

다이얼을 구현하는 부품들이다. 대부분 orchestration 계층에 들어간다.

### 3.1 행동 분류 (risk tier)

모든 tool에 위험도를 붙인다. 이것이 다른 모든 메커니즘의 기초다.

| Tier | 정의 | 예 | 기본 정책 |
|---|---|---|---|
| **Read** | 세계를 바꾸지 않음 | 파일 읽기, 검색, 조회 | 자동 |
| **Reversible write** | 바꾸지만 되돌릴 수 있음 | git 안의 파일 수정, 임시 파일 생성 | 자동 + 사후 검토 |
| **Irreversible write** | 되돌릴 수 없음 | 파일 삭제, DB 변경, `git push --force` | 승인 |
| **External** | 제3자에게 영향 | 이메일 발송, 결제, 공개 게시 | 승인 (항상) |

Tool을 만드는 사람이 tier를 선언한다. 선언하지 않은 tool은 가장 높은 tier로 취급한다.

### 3.2 정책 규칙 (allow / ask / deny)

Tier별 기본 정책 위에 사용자가 규칙을 덧붙인다.

```
allow  read:*                        # 읽기는 전부 자동
allow  write:src/**                  # src 아래 수정은 자동
allow  bash:npm test                 # 이 명령은 자동
ask    write:**                      # 그 외 쓰기는 물어봐
deny   bash:rm -rf *                 # 이건 절대 금지, 묻지도 말고
deny   external:*                    # 외부 발송은 이 프로젝트에서 금지
```

규칙은 **범위별로 겹친다.** 사용자 전체 설정 → 프로젝트 설정 → 이번 세션 설정. 좁은 범위가 우선한다. 이렇게 하면 "평소엔 보수적, 이 프로젝트에선 관대하게, 이 세션만 더 관대하게"가 가능하다.

### 3.3 승인 요청의 품질

L1–L2에서 사용자가 보는 것은 승인 요청이다. 이 요청의 품질이 다이얼 전체의 품질을 결정한다. 나쁜 요청은 읽히지 않고, 읽히지 않는 승인은 없는 것과 같다.

좋은 승인 요청은 네 가지를 담는다.

| 항목 | 나쁜 예 | 좋은 예 |
|---|---|---|
| **무엇을** | "명령을 실행합니다" | `rm build/cache/*.tmp` (파일 47개) |
| **왜** | (없음) | 빌드 캐시가 손상되어 재생성이 필요 |
| **되돌릴 수 있나** | (없음) | 되돌릴 수 없음. 단, 다음 빌드에서 자동 재생성됨 |
| **영향 범위** | (없음) | `build/cache/` 안에서만. 소스 파일 영향 없음 |

그리고 응답 선택지에 **"이번만" / "이 세션 동안" / "항상"**을 둔다. 사용자가 "항상"을 고르면 그것이 3.2의 규칙으로 저장된다. 다이얼이 사용 중에 자연스럽게 올라가는 경로다.

### 3.4 승인 피로 (approval fatigue) 방지

승인 요청이 많으면 사용자는 읽지 않는다. 그 순간부터 L1은 L3보다 위험하다. **사용자는 자기가 통제하고 있다고 믿지만 실제로는 아무것도 보지 않는다.**

- **Read tier는 묻지 않는다.** 물을 가치가 없는 것을 물으면 물을 가치가 있는 것도 안 읽힌다
- **묶어서 묻는다.** 파일 12개 수정을 12번 묻지 말고, 계획 한 번을 보여주고 한 번 묻는다
- **반복되면 제안한다.** 같은 종류의 요청을 세 번 승인하면 "이 종류는 자동으로 할까요?"를 제안한다
- **승인 요청 수를 지표로 본다.** 세션당 승인 요청이 늘고 있으면 정책이 잘못된 것이다

### 3.5 Plan-then-execute

승인 횟수를 줄이면서 통제를 유지하는 가장 효과적인 패턴이다. Agent가 먼저 **계획**을 세우고(어떤 파일을 어떻게 바꿀지, 어떤 명령을 실행할지), 사용자가 계획을 한 번 승인하면, 실행은 그 계획 안에서 자율적으로 한다.

```
L1:  행동1 [승인] 행동2 [승인] 행동3 [승인] ... 행동20 [승인]      → 승인 20회
계획: [계획 승인] 행동1 행동2 행동3 ... 행동20 [결과 검토]         → 승인 1회 + 검토 1회
```

계획에서 벗어나는 행동(계획에 없던 파일, 예상 밖 오류)은 다시 물어본다. 계획은 사용자가 승인한 **경계**가 된다.

### 3.6 경계와 예산

레벨을 올릴 때 반드시 함께 조여야 하는 것들이다. 개입 시점이 뒤로 밀린 만큼, 사고가 났을 때 피해가 어디까지 갈 수 있는지를 미리 제한한다.

| 경계 | 예 |
|---|---|
| **파일 범위** | 이 디렉터리 밖은 건드리지 않음 |
| **네트워크** | 허용된 도메인만 |
| **자원** | max steps, max cost, max wall-clock |
| **실행 환경** | sandbox, 격리된 branch, 별도 계정 |

**L3에 경계가 없으면 L4와 같다.** "감독하고 있으니 괜찮다"는 사용자가 화면을 보고 있을 때만 참이다.

### 3.7 실행 중 개입

L3의 핵심이다. Agent가 자율적으로 돌고 있는 동안 사용자가 할 수 있어야 하는 것:

- **보기**: 지금 무엇을 하고 있는지 실시간으로. 무엇을 했는지 이력으로
- **말하기**: 실행을 멈추지 않고 방향 수정("그 파일은 건드리지 마")
- **멈추기**: 즉시 중단. 진행 중인 tool 호출도 취소
- **되돌리기**: 마지막 checkpoint로. Git commit, 파일 snapshot, DB transaction

되돌리기가 있으면 사용자는 레벨을 더 쉽게 올린다. "틀려도 되돌릴 수 있다"가 신뢰의 전제다.

### 3.8 Agent의 escalation

Agent가 스스로 다이얼을 내리는 조건을 명시한다.

- 지시가 두 가지 이상으로 해석되고, 해석에 따라 결과가 크게 다를 때
- 예상한 상태와 실제가 다를 때 (파일이 있어야 하는데 없다, 테스트가 이미 실패 중이다)
- 영향 범위가 예상보다 클 때 (3개 파일인 줄 알았는데 300개)
- 되돌릴 수 없는 행동인데 계획에 없었을 때
- 같은 오류가 반복될 때

이 조건들은 system prompt에도 쓰지만, **orchestration 코드에서도 감지한다.** "파일 300개 이상 영향" 같은 것은 코드가 확실하게 잡는다.

### 3.9 감사 기록

레벨이 높을수록 사후 감사가 사전 승인을 대체한다. 따라서 L3–L4는 **모든 행동의 trace**가 전제다. 무엇을, 왜, 어떤 근거로, 어떤 결과가 나왔는지. Trace 없는 L4는 "무슨 일이 일어났는지 아무도 모르는 모드"다.

### 3.10 신뢰의 단계적 확대

시간에 따른 다이얼 이동을 시스템이 지원한다.

- 같은 종류의 작업이 N번 연속 문제없이 승인되면 자동화를 **제안**한다 (자동으로 올리지는 않는다)
- 사고가 나면(사용자가 되돌리기를 했다, 중단했다) 해당 종류의 레벨을 **자동으로 내리고** 알린다
- 새 tool, 새 프로젝트, 새 사용자는 낮은 레벨에서 시작한다

올리기는 사람이, 내리기는 시스템이 해도 된다. 비대칭이 의도다.

## 4. 레벨을 올릴 때 함께 바꿀 것

레벨은 혼자 움직이지 않는다. 한 칸 올리면 다른 것을 조여야 균형이 맞는다.

| 올리는 것 | 함께 조이는 것 |
|---|---|
| L1 → L2 | Tier 분류가 정확한지 확인. Ask 대상이 실제로 위험한 것들인지 |
| L2 → L3 | 경계(파일, 네트워크, 예산) 설정. 되돌리기 수단 확보. 실시간 관찰 수단 |
| L3 → L4 | Sandbox 격리. 완전한 trace. 알림(실패, 예산 초과). 정기 감사 절차 |

"레벨만 올리고 나머지는 그대로"가 사고의 전형적인 전조다.

## 5. Worked Example — 한 사용자의 4주

코드 리팩토링을 돕는 agent를 처음 쓰는 개발자.

| 시점 | 레벨 | 일어난 일 |
|---|---|---|
| Day 1 | L1 | 모든 tool 호출을 승인. 파일 읽기 요청 30번에 지친다 |
| Day 2 | L2 | "읽기는 자동으로"를 켠다. 승인 요청이 세션당 30회 → 5회 |
| Week 1 | L2 | 테스트 파일 수정 승인을 반복. 시스템이 "테스트 파일 수정은 자동으로 할까요?" 제안. 수락 |
| Week 2 | L3 (부분) | `src/` 안 수정은 자동, `git push`는 승인. Plan-then-execute로 큰 리팩토링을 계획 1회 승인으로 처리. 완료 후 diff 검토 |
| Week 3 | L3 | Agent가 리팩토링 중 설정 파일을 잘못 수정. 사용자가 rollback. 시스템이 설정 파일 수정을 ask로 자동 강등하고 알림 |
| Week 4 | L3 + L4 (일부) | 야간에 "lint 오류 자동 수정" 작업을 L4로 스케줄. Sandbox branch에서 실행, 아침에 PR로 검토 |

4주 동안 사용자는 코드를 한 줄도 고치지 않았고 설정 파일을 열지 않았다. 다이얼은 대화와 클릭으로만 움직였다. Week 3의 사고는 되돌리기 한 번으로 끝났고, 시스템이 스스로 한 칸 내렸다.

## 6. 실패 패턴

| 패턴 | 증상 | 원인 |
|---|---|---|
| **이분법** | 사용자가 "전부 허용" 모드에만 산다 | 중간 레벨이 없거나 쓰기 어렵다 |
| **승인 피로** | 승인율 99%, 읽는 시간 0.5초 | Read tier까지 묻는다. 묶어서 묻지 않는다 |
| **맥락 없는 승인** | "명령을 실행할까요? [Y/n]" | 무엇을, 왜, 되돌릴 수 있나가 없다 |
| **내리기 어려움** | 사고 중인데 설정 화면을 찾고 있다 | Stop/pause/rollback이 한 동작이 아니다 |
| **경계 없는 L3** | "감독 중"이었는데 홈 디렉터리가 지워졌다 | 레벨만 올리고 범위 제한을 안 했다 |
| **묻지 않는 agent** | 모호한 지시를 추측으로 실행 | Escalation 조건이 없다 |
| **묻기만 하는 agent** | 명확한 지시에도 "정말요?" | Escalation 조건이 너무 넓다 |
| **Trace 없는 L4** | 무슨 일이 있었는지 아무도 모른다 | 사후 감사 수단 없이 사전 승인만 뺐다 |

## Checklist

**다이얼이 있나**
- [ ] 자율성 레벨이 셋 이상이고, 사용자가 선택할 수 있다
- [ ] 행동 종류, 범위, 자원, 맥락 축이 독립적으로 설정된다
- [ ] 설정 변경에 코드 수정이나 재배포가 필요하지 않다

**부드럽게 움직이나**
- [ ] 승인 요청에서 "항상 허용"을 고르면 규칙으로 저장된다
- [ ] 같은 종류의 승인이 반복되면 자동화를 제안한다
- [ ] Stop, pause, rollback이 각각 한 동작이다
- [ ] 사고(rollback, 중단) 후 해당 종류의 레벨이 내려가고 알림이 온다

**안전하게 올라가나**
- [ ] 모든 tool에 risk tier가 선언되어 있다
- [ ] Read tier는 승인을 요구하지 않는다
- [ ] L3 이상에는 파일/네트워크/예산 경계가 있다
- [ ] L4에는 sandbox와 완전한 trace가 있다

**Agent가 스스로 내려오나**
- [ ] 지시가 모호하거나 영향 범위가 예상 밖이면 물어본다
- [ ] 계획에 없던 irreversible 행동은 승인을 요구한다
- [ ] Escalation 조건 일부는 prompt가 아니라 코드로 감지된다

**승인이 읽히나**
- [ ] 승인 요청에 무엇을, 왜, 되돌릴 수 있나, 영향 범위가 있다
- [ ] 여러 행동을 계획 하나로 묶어 한 번에 승인받을 수 있다
- [ ] 세션당 승인 요청 수를 지표로 추적한다
