# Versioning의 중요성

Product를 운영하다 보면 "고객사 A에서 이런 버그가 났어요"라는 리포트를 받는 순간이 반드시 온다. 이때 가장 먼저 필요한 정보는 **그 환경에 어떤 버전이 배포되어 있는가**다. 버전을 모르면 어떤 코드가 돌고 있는지 특정할 수 없고, 재현도 원인 분석도 시작할 수 없다.

## 왜 중요한가

- **디버깅의 출발점**: 버전을 알면 해당 시점의 소스 코드(tag/commit)를 정확히 checkout 해서 같은 조건으로 재현할 수 있다. 버전이 없으면 "지금 main 코드"와 "고객 환경 코드"가 다를 수 있다는 사실조차 확인하기 어렵다.
- **이미 고친 버그인지 판별**: 리포트된 문제가 v1.2.3에서 이미 수정된 것이라면, 원인 분석 대신 "v1.2.4로 업데이트하세요"라는 답으로 끝난다. 버전 정보 하나가 수 시간의 분석을 아껴준다.
- **배포 범위 파악**: 특정 버전에 심각한 결함이 발견됐을 때, 어떤 고객/서버가 그 버전을 쓰고 있는지 알아야 영향 범위를 산정하고 롤백·패치 대상을 정할 수 있다.
- **여러 컴포넌트 간 호환성**: agent, server, driver처럼 여러 모듈이 함께 배포되는 제품은 조합에 따라 동작이 달라진다. 각 모듈의 버전이 명확해야 "이 조합에서만 터지는 문제"를 좁힐 수 있다.

## 실천 방법

1. **모든 배포물에 버전을 박는다.** 실행 파일, 라이브러리, 컨테이너 이미지, 설치 패키지 — 예외 없이. `--version` 플래그, About 화면, 로그 첫 줄 등 사용자가 쉽게 확인할 수 있는 곳에 노출한다.
2. **버전과 소스 코드를 1:1로 연결한다.** release 시점에 git tag를 남기고, 빌드 시 commit hash를 함께 embed 하면 (`v1.2.3+abc1234`) 어떤 버전이든 정확한 코드로 되돌아갈 수 있다.
3. **[Semantic Versioning](https://semver.org/)** 같은 일관된 규칙을 따른다. `MAJOR.MINOR.PATCH`만 지켜도 버전 번호만으로 변경의 성격(breaking change 여부)을 짐작할 수 있다.
4. **로그에 버전을 남긴다.** 프로세스 시작 시 버전과 build 정보를 로그에 출력해두면, 고객이 보내준 로그 파일만으로도 버전을 특정할 수 있다.
5. **CHANGELOG를 유지한다.** 버전별 변경 내역이 있어야 "이 문제가 어느 버전부터 생겼는가"를 코드를 뒤지지 않고도 좁힐 수 있다.

## 한 줄 요약

> 배포된 곳마다 어떤 버전이 돌고 있는지 즉시 알 수 있어야 디버깅이 쉬워진다. 버전 없는 배포물은 추적 불가능한 블랙박스다.
