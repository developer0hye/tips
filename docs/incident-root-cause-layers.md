# 원인은 하나가 아니다 — 디스크가 가득 찬 서버를 37일간 몰랐던 이유

개인 프로필 사이트를 올려둔 `t3.micro` 한 대가 **37일 동안 CPU 95%로 돌았다.** 아무도 몰랐고, 청구서가 와서야 알았다. 그달 요금은 $101.06.

원인을 물으면 "디스크가 꽉 차서"라고 답하게 된다. 맞지만, 그 답으로는 **왜 돈이 나갔는지도, 왜 한 달이나 걸렸는지도** 설명되지 않는다. 실제로는 세 겹이었다.

## 먼저 청구서를 쪼갠다

"디스크 때문에 $101이 나왔다"는 틀린 요약이다.

| 항목 | 금액 | 원인 |
|---|---|---|
| CPU 크레딧 초과 | **$61.62** | 디스크 가득 참 |
| EC2 컴퓨팅 | $19.34 | **프리티어 만료** — 무관 |
| 세금 | $9.18 | |
| 공인 IP 2개 | $7.44 | 평소 비용 |
| EBS | $3.47 | 평소 비용 |

디스크가 설명하는 건 **61%**다. 나머지는 하필 같은 주(6/27)에 계정 생성 12개월이 지나 프리티어가 끝난 것이고, 이게 체감 충격을 키웠다.

**원인 분석에서 가장 먼저 할 일은 이 분리다.** 두 사건이 겹친 걸 하나로 보면, 하나를 고치고 "해결했다"고 믿게 된다.

## 1층 — 방아쇠: 디스크가 찼다

8GB 디스크의 내역은 이랬다.

```
사용 가능        6.8 GB
├─ swapfile      2.0 GB  ← 29%. RAM 1GB짜리에 2GB 스왑
├─ /usr          2.0 GB
├─ actions-runner 1.3 GB
└─ /var          1.4 GB
                ───────
                 6.7 GB 사용 / 남은 공간 7.1 MB
```

러너 1.3GB의 절반이 쓰레기였다. GitHub Actions 러너는 **자기 자신을 업데이트하면서 구버전을 지우지 않는다.** 버전마다 Node.js 런타임을 네 벌씩(node20, node24, 각 alpine) 넣어두므로 한 세대가 ~600MB다.

```
externals.2.331.0   591 MB   현재
externals.2.322.0   266 MB   ← 구버전, 안 지워짐
bin.2.331.0          79 MB
bin.2.322.0          79 MB   ← 구버전, 안 지워짐
_work/_update       193 MB   ← 적용 완료된 업데이트 패키지
```

**설치한 순간부터 차오르는 게 예정돼 있었다.** 6월 말 193MB 업데이트를 받으면서 마지막 여유가 사라졌을 뿐이다.

디스크가 100%가 되자:

- 러너가 로그조차 못 써서 **시작하자마자 크래시** → 0바이트 로그 파일 3,643개
- systemd가 재시작 → 또 크래시 → 하루 104회
- `rsyslogd`, `journald`도 못 쓰는 로그를 계속 시도 (하루 2,405회 실패 기록)

이 헛도는 프로세스들이 CPU를 채웠다.

## 2층 — 증폭기: `unlimited` 모드

여기가 핵심이고, 대부분 이 층을 빠뜨린다.

T 시리즈는 baseline(t3.micro는 10%)을 넘으면 CPU 크레딧을 쓴다. 크레딧이 바닥나면 두 갈래로 갈린다.

| 모드 | 크레딧 소진 후 | 결과 |
|---|---|---|
| `unlimited` (**기본값**) | 계속 돌고 시간당 과금 | **$61.62** |
| `standard` | baseline으로 스로틀링 | **$0** |

**`standard`였다면 똑같은 크래시 루프가 $0였다.** 사이트가 느려졌을 뿐이다.

즉 필요조건이 둘이고, 어느 하나만으로는 이 결과가 안 나온다.

| | 디스크 정상 | 디스크 가득 참 |
|---|---|---|
| **`standard`** | 정상 | 사이트 느려짐, **$0** |
| **`unlimited`** | 정상 | **$61.62** |

원인을 "디스크"로만 적으면, 디스크를 키우고 안심하게 된다. 그러면 다음에 디스크가 아닌 다른 이유로 CPU가 튈 때 똑같이 당한다.

## 3층 — 왜 37일이었나

돈이 나간 것보다 **한 달간 아무도 몰랐다**는 게 더 큰 문제다. 감시가 네 군데서 실패했다.

**① EC2는 디스크 사용률을 CloudWatch에 보내지 않는다.**
CPU·네트워크는 기본으로 보내는데 디스크는 안 보낸다. CloudWatch 에이전트를 따로 깔아야 한다. 정작 터진 지표를 아무도 안 보고 있었다.

**② 관측 도구가 관측 대상 자원을 공유했다.**
`sysstat`은 설치돼 있었다. 그런데 **꽉 찬 디스크에는 기록을 못 한다.** 사후에 "6/26에 무슨 일이 있었나"를 보려 했더니 그 구간만 비어 있었다.

> 감시 도구가 감시 대상 자원에 의존하면, 정확히 필요한 순간에 죽는다.

로그를 디스크에 쓰는 모든 도구가 디스크 장애에 대해 이 성질을 갖는다. 그래서 디스크 여유 알람만은 **외부에서** 봐야 한다.

**③ `unlimited`이 증상을 지웠다.**
성능이 정상으로 유지되니 볼 게 없었다. 사용자도 정상으로 느꼈다. `standard`였다면 "왜 이렇게 느리지?"가 하루 안에 나왔을 것이다.

> 성능 저하는 즉시 오는 신호고, 초과 과금은 30일 뒤에 오는 신호다.

**④ 감지는 됐는데 알림이 닿지 않았다.**
AWS Cost Anomaly Detection이 켜져 있었고, **6/26 당일에 실제로 감지했다.** 6/28, 7/02에도 다시 울렸다. 시스템은 완벽하게 작동했고 메일이 묻혔을 뿐이다.

이건 흔한 실패라 따로 적어둘 가치가 있다. **알림을 하나 더 추가하는 건 해결이 아니다.** 안 읽는 받은편지함에 한 통 더 쌓일 뿐이다. 임계값을 실제로 시끄럽게 잡거나(평소 하루 $0.31인데 $1에 알람), 채널을 바꿔야 한다.

## 정리하면

```
디스크가 찬다        ← 방아쇠
   ↓
크래시 루프로 CPU 100%
   ↓
unlimited이 요금으로 변환   ← 증폭기
   ↓
감시 부재로 37일 방치       ← 지속시간
   ↓
$61.62
```

**방아쇠만 고치면 형태만 바꿔서 재발한다.** 디스크를 20GB로 키워도, CPU를 태우는 다른 원인이 생기면 `unlimited`은 여전히 그걸 요금으로 바꾼다.

## 실천 방법

1. **T 시리즈는 `standard`로 둔다.** 개인 서버·사내 도구처럼 평소 CPU를 안 쓰는 경우 잃는 게 없고, 이상 상황에서 스로틀링이 오히려 조기 경보가 된다. 트래픽이 실제로 튀는 서비스라면 `unlimited`을 유지하되 **반드시 일일 예산 알림을 건다.**
2. **디스크 여유 알람을 건다.** EC2 기본 지표에 없으니 CloudWatch 에이전트를 깔거나, 서버에서 주기적으로 검사한다. **inode도 같이 본다** — 작은 파일이 쏟아지면 용량보다 inode가 먼저 고갈되는데 `df` 기본 화면에는 안 보인다.
3. **월 예산이 아니라 일 예산으로 건다.** 이번 건은 하루 $2씩 32일에 걸쳐 쌓였다. 월 예산 80% 알림은 3주 뒤에나 울린다.
4. **자체 업데이트하는 에이전트에는 정리 정책을 붙인다.** CI 러너, 자동 업데이터 종류는 구버전을 안 지운다. 설치했다면 정리도 같이 설계한다.
5. **서버에서 빌드하지 않는다.** 빌드는 디스크와 CPU를 동시에 크게 먹는다. CI나 로컬에서 만들어 산출물만 보내면 운영 서버가 조용해지고 `standard` 모드와도 잘 맞는다.
6. **알림이 실제로 도착하는지 확인한다.** 구독이 `PendingConfirmation`인 채로 방치된 SNS, 스팸함으로 가는 예산 알림은 없는 것과 같다. 만들고 나서 한 번은 실제로 받아본다.

## 한 줄 요약

> 방아쇠, 증폭기, 감지 실패를 분리해서 적어라. "디스크가 찼다"만 고치면 다음엔 다른 방아쇠로 똑같이 당한다.
