# AI-Native SDLC — 코드가 병목이 아니게 된 다음, 프로세스를 어떻게 바꾸나

에이전트가 diff의 대부분을 쓰기 시작하면 팀에서 가장 먼저 무너지는 건 코드 품질이 아니라 **코드 주변의 절차**다. 계획, 리뷰, 배포 승인이 여전히 사람 속도로 돌기 때문이다. Anthropic Applied AI 팀이 고객사에 적용해온 방식을 6단계 14개 플레이로 정리한 것이 [The AI-Native SDLC Playbook](https://academy.claude.com/courses/ai-native-sdlc-playbook)이고, 이 문서는 그 전문을 읽고 **"우리 팀에 무엇부터 어떻게 얹을 것인가"** 관점으로 압축한 것이다.

> 원문은 무료 공개 강좌다. 이 문서는 요약이므로, 설정 키나 스크립트를 실제로 쓸 때는 원문과 하단 [§10 더 볼 것](#10-더-볼-것)의 공식 문서를 확인할 것.

---

## 1. 왜 알아야 하나

### 겪는 증상에서 출발하기

| 겪는 증상 | 원인 | 절 |
|---|---|---|
| 에이전트가 코드는 30분에 짜는데 머지까지 2주 걸린다 | 병목이 build 밖으로 이동했는데 절차는 그대로 | §2 |
| 요구사항이 전달되면서 원래 의도와 달라진다 | 핸드오프마다 소유권이 넘어감. 아티팩트가 없음 | §3 |
| 리뷰 큐가 계속 쌓인다. 혹은 미검토 코드가 나간다 | 리뷰 용량이 사람 산출량 기준으로 잡혀 있음 | §6 |
| 에이전트가 같은 실수를 반복한다 | 교정이 세션 안에서 끝나고 파일로 남지 않음 | §4 |
| 정책을 문서로 써뒀는데 안 지켜진다 | 스킬은 권고다. 강제는 훅의 몫 | §5 |
| CLAUDE.md를 고쳤는데 더 나아졌는지 알 수 없다 | 설정 변경에 회귀 테스트가 없음 | §7 |
| 에이전트에게 배포를 못 맡기겠다 | 환경별 자율성 계층과 승인 게이트가 없음 | §8 |
| 인시던트 후속 조치가 코드에 반영되지 않는다 | 루프가 닫히지 않음 | §9 |

### 역할별로 어디까지 읽으면 되나

전부 읽을 필요는 없다. 플레이는 모듈이고 각자 전제 조건이 다르다.

| 역할 | 필요한 절 |
|---|---|
| 개발자 | §3 아티팩트 체인, §4 CLAUDE.md, §5 스킬, §6 피드백 루프 |
| 테크리드 | 위 + §6 REVIEW.md, §7 설정 eval |
| 플랫폼·보안 | 위 + §8 훅과 managed settings, §9 루프 자동화 |
| 엔지니어링 리더십 | §2 전제, §10 도입 순서와 측정 지표 |

### 팀 규모에 따라

원문은 대기업, 특히 규제 산업을 상정하고 쓰였다. 명시된 전제 조건도 Claude Code를 일상적으로 쓰고 있고 **바꿀 권한이 있는 Git 저장소와 CI 파이프라인**을 가진 팀이다.

작은 팀이라면 [§9 도입 순서](#9-무엇부터-할-것인가)의 1번에서 5번까지가 값의 대부분을 준다. `intent.md`와 `spec.md`의 단계 분리, managed settings, 루프 자동화는 **핸드오프가 실재하고 승인 주체가 나뉘어 있을 때** 값이 생긴다. 한 사람이 제안자이자 리뷰어이자 배포자인 팀에서는 아티팩트만 남기고 게이트는 생략하는 편이 낫다. 게이트가 자기 자신을 승인하는 절차가 되면 서류만 늘고 통제는 없다.

## 2. 전제 — 병목은 사라지지 않고 이동한다

전통적 SDLC는 **코드 작성이 가장 비싼 단계**라는 전제 위에 설계됐다. PRD, 산정 의식, 보안 리뷰는 몇 주에서 몇 분기에 걸친 개발 기간 동안 정렬을 강제하기 위해 존재했다.

그 전제가 깨지면 세 가지가 동시에 벌어진다.

- **병목이 양옆으로 옮겨간다.** build는 에이전트 속도로 붕괴하고, plan과 review와 deploy는 사람 속도로 남는다
- **통제가 현실과 어긋난다.** 사람이 쓴 코드를 한 줄씩 읽는 건 말이 됐다. 에이전트가 diff의 대부분을 쓰면 따라갈 수 없다
- **거버넌스 비용이 오른다.** 예외는 여전히 주간이나 월간으로 모이는 회의를 통과해야 한다

보안 조직이 가장 먼저 부딪힌다. 인원이 사람 산출량에 맞춰 잡혀 있어서, 에이전트가 코드량을 늘리면 **리뷰 큐가 쌓이거나 미검토 코드가 나간다.** 규제 산업에서는 둘 다 받아들일 수 없다.

**이걸 알면 무엇이 달라지나.** "에이전트 도입했는데 왜 배포 주기가 그대로지"라는 질문의 답이 나온다. 구현 단계만 바꾸고 나머지를 그대로 두면, 전체 리드타임은 가장 느린 단계가 결정한다. 도입 효과가 안 보이는 게 아니라 **측정 지점이 틀린 것**이다.

## 3. 핵심 개념 — 아티팩트 체인

플레이북 전체를 한 문장으로 줄이면 이것이다.

> **각 단계는 아티팩트를 버전 관리에 커밋하며 끝나고, 다음 단계는 그것을 읽으며 시작한다.**

| 단계 | 아티팩트 | 누가 승인하나 |
|---|---|---|
| Plan | `intent.md` | 제품 오너 |
| Design | `spec.md` | 제품 오너 |
| Build | `plan.md`, diff, 테스트 | 엔지니어, 고위험은 테크리드 |
| Test | 테스트·빌드 출력, eval 결과 | 코드 오너 |
| Deploy | 리뷰 소견이 붙은 PR | 코드 오너, 릴리스는 릴리스 매니저 |
| Maintain | 인시던트 기록 → 다음 `intent.md` | 서비스 오너 |

초기 단계가 `.md`인 이유는 **제품 오너와 에이전트가 같은 파일을 읽고 실행할 수 있어서**다. Build부터는 아티팩트가 코드와 그 기록으로 바뀐다.

**활용 맥락.** 커밋 체인이 곧 감사 추적이 된다. 누가 무엇을 요청했고, 에이전트가 무엇을 만들었고, 누가 승인했는지가 **하나의 타임스탬프 권위** 아래 남는다. 규제 대응에서 "이 코드가 왜 이렇게 됐는지 증명하라"는 요구에 Git 히스토리로 답할 수 있다는 뜻이다.

그리고 프로세스가 선형이 아니라 **루프**가 된다. 승인된 `intent.md`가 요구사항 패스를 트리거하고, 승인된 `spec.md`가 plan mode를 트리거하고, 병합된 PR이 파이프라인을 트리거하고, 프로덕션의 컨트롤 밴드 위반이 다음 `intent.md`를 쓴다.

처음에는 각 단계를 손으로 프롬프팅한다. 최종 상태는 **승인된 아티팩트가 다음 게이트를 자동으로 발사하는 루프**다. 사람의 주의는 게이트에 몰린다. 매번 처음부터 시작하는 대신, 에이전트가 플래그를 세운 것만 본다.

### 레거시 시스템과의 공존

Jira, ServiceNow, 요구사항 관리 도구가 이미 기록을 들고 있다면 셋 중 하나를 고른다.

| 배치 | 진실의 원천 | 언제 맞나 |
|---|---|---|
| repo가 진실 | Markdown 아티팩트. 레거시는 커밋을 참조 | 엔지니어링 주도 조직. 가장 깔끔함 |
| 레거시가 진실 | Jira 등. Markdown은 작업 사본 | 감사인이 이미 그 도구를 승인한 경우 |
| 연결만 | 양쪽 없음. 상호 ID 기재 | **전환 시작점.** 아티팩트에 레코드 ID, 레코드에 커밋 SHA |

**활용 맥락.** 대부분의 조직은 세 번째부터 시작해야 한다. 감사인과 다른 팀이 이미 레거시 도구에 의존하고 있어서 한 번에 밀어낼 수 없기 때문이다. 중요한 건 **아티팩트마다 원천을 하나로 지정**하는 것이지 도구를 통일하는 게 아니다.

## 4. Plan과 Design — 의도를 파일로 고정한다

### intent.md

아이디어의 출발점이 사람이든, 티켓이든, 알림이든 절차는 같다.

1. 제안자가 자기 말로 문제를 Claude에게 설명한다. 형식 언어는 필요 없다
2. 구체화될 때까지 브레인스토밍한다. Claude가 분석가가 물을 질문을 한다. 범위, 사용자, 제약, 성공의 정의
3. 조직 템플릿에 맞춰 `intent.md`로 쓰게 한다. 템플릿 자체를 스킬로 인코딩할 수 있다
4. 제안자가 오해된 부분을 고친다
5. 공유 저장소에 커밋한다. 작성자와 타임스탬프가 기록에 합류한다

```markdown
# Intent: 청구 상태 셀프서비스
Author: J. Ortiz (claims operations). Status: draft.

## Problem
고객이 청구 진행 상황을 물으려고 콜센터에 전화한다.
상담사 통화 시간의 약 1/3이 상태 조회에만 쓰인다.

## Proposed outcome
고객이 포털에서 청구 상태, 다음 단계, 예상 일자를 직접 본다.

## Affected users and systems
청구 상담사, 포털 팀, claims-core API.

## Constraints
포털 세션에 새로운 PII를 추가하지 않는다. 기존 인증만 사용.

## Open questions
제3자 손해사정인도 접근이 필요한가?
```

**활용 맥락.** 기존 방식에서는 아이디어가 백로그 항목, 유저 스토리, 스토리 포인트, 리파인먼트 회의를 거친다. **핸드오프마다 소유권이 넘어가서** 엔지니어링에 도착할 때쯤이면 원래 의도와 여러 단계 떨어져 있다. `intent.md`는 제안자의 언어로 된 기록을 고정해서 이 손실을 막는다.

Git 경험이 없는 기여자도 된다. claude.ai나 Cowork에서 버전 관리 시스템 커넥터를 통해 Claude가 대신 커밋한다.

### spec.md

제품 오너가 `intent.md`를 승인하면 Claude가 요구사항·설계 스펙을 만든다. 조직의 브랜드·보안·컴플라이언스·UX 정책이 **스킬로 인코딩되어 있어야** 이 단계가 제대로 굴러간다.

핵심은 **제품 오너가 스펙을 검토하되 쓰지는 않는다**는 것이다. 목표는 엔지니어링 팀이 계획을 세울 수 있는 스펙이고, 우려 지점에는 플래그가 붙어 있어야 한다.

### plan.md

엔지니어는 Claude Code를 **plan mode로 시작**한다. plan mode에서 Claude는 코드베이스를 읽을 수 있지만 고칠 수는 없다.

```markdown
# Plan: 청구 상태 셀프서비스 (intent.md 2026-06-02 기준)

## 바뀌는 파일
portal/src/claims/StatusPanel.tsx (신규)
claims-api/routes/status.py
claims-api/tests/test_status.py

## 작업 순서
1. 기존 인증 뒤에 상태 엔드포인트 추가
2. 엔드포인트에 맞춰 패널 구현
3. 포털 네비게이션에 연결

## 위험
claims-core API가 50 rps에서 rate limit. 패널은 캐시해야 한다.

## 증명
test_status.py가 4가지 청구 상태를 커버. 스크린샷이 승인된 목업과 일치.
```

계획을 그냥 받지 말고 **심문한다.** 이 변경이 무엇을 깨뜨릴 수 있나, 어느 단계가 가장 위험한가, 선택하지 않은 다른 방법은 무엇인가. **이 대화를 본 적 없는 엔지니어가 계획만으로 구현할 수 있을 때까지** 반복한다.

**활용 맥락.** 기존에는 "어떻게 고칠 것인가"가 엔지니어의 머릿속이나 잘해야 티켓 코멘트에 있었다. 아무도 리뷰할 수 없고, 리뷰어가 처음 보는 건 완성된 diff다. 그때는 재작업이 비싸다. **설계 리뷰를 코드 생성 전으로 옮기면**, 방향을 바꾸는 일이 문서 편집 수준의 비용이 된다. plan mode는 이걸 스스로 강제한다. 엔지니어가 계획을 수락하기 전까지 Claude가 파일을 고칠 수 없기 때문이다.

구현이 계획에서 벗어나면 **같은 커밋에서 `plan.md`를 갱신**한다. 훅으로 동기화를 강제할 수 있다. 나중에 PR 리뷰가 diff를 `plan.md`와 대조한다.

## 5. Build — 지식을 파일로, 정책을 훅으로

### CLAUDE.md는 한 페이지를 넘기지 않는다

새로 합류한 사람이 첫날 필요한 것만 남긴다. 빌드·테스트·린트 명령, 중요한 컨벤션, 그리고 **Claude가 자꾸 틀리는 것.**

```markdown
# Payments service

## Commands
- Build: make build
- Test: make test (unit), make itest (integration, docker 필요)
- Lint: make lint

## Conventions
- Java 21, Spring Boot 3. 새 Lombok 금지.
- 금액은 항상 BigDecimal, 절대 double 아님.

## Things Claude gets wrong
- 의존성 버전 올리지 말 것. 플랫폼 팀 소유.
- 레거시 v1/ 패키지는 동결. 변경은 v2/에서.
```

운영 규칙 하나가 이 파일을 살아있게 만든다. **Claude가 같은 실수를 두 번 하면 그 교정이 CLAUDE.md로 들어간다.**

**활용 맥락.** 분량 제한에는 이유가 있다. Claude는 세션 시작마다 이 파일을 **전부** 읽는다. 낡은 내용은 아무 이득 없이 컨텍스트를 먹는다. 파일이 수백 줄로 자랐다면 그건 매뉴얼이지 컨텍스트 헤더가 아니다. 조건부로만 필요한 절차는 **스킬로 내려서 트리거될 때만 로드**시켜야 한다.

### 스킬은 권고, 훅은 강제

이 구분이 플레이북에서 가장 이식성 높은 개념이다.

| | 스킬 | 훅 |
|---|---|---|
| 성격 | 조언적 통제 | 결정적 통제 |
| 동작 | Claude가 정책을 적용할 **가능성을 높인다** | 매번, 모두에게 적용된다 |
| 실패 모드 | 세션이 따르지 않아도 막을 방법이 없다 | 없음. exit 2면 행동이 차단된다 |
| 위치 | `.claude/skills/<name>/SKILL.md` | `.claude/settings.json` 또는 managed settings |

> **항상 성립해야 하는 정책에는 스킬 뒤에 결정적인 것이 필요하다.** 스킬이 위반을 드물게 만들고, 훅이 위반을 거의 불가능하게 만든다.

스킬은 frontmatter가 **언제 발동할지**를, 본문이 **무엇을 할지**를 말하는 폴더다.

```markdown
---
name: secure-api-review
description: API 보안 표준 적용. 외부 노출 엔드포인트를 만들거나 수정할 때,

# Secure API review
1. 인증: 모든 엔드포인트는 게이트웨이 JWT 필요. /health 외 익명 라우트 금지
2. 입력 검증: OpenAPI 스키마로 본문 검증, 알 수 없는 필드는 거부
3. 감사: 상태 변경 엔드포인트는 actor, action, entity, timestamp 감사 이벤트 발생
4. 데이터 분류: 스키마에서 pii 태그가 붙은 필드는 로그와 에러 메시지에 절대 노출 금지
```

**활용 맥락.** 빌드 단계 훅의 실전 용도는 이렇다.

- 생성된 클래스나 동결된 패키지 같은 **보호 경로 편집 차단**
- 파일 편집 후 포매터·린터 실행으로 드리프트 누적 방지
- 자격증명이 diff에 들어가는 것 차단
- 예외 없이 성립해야 하는 스킬의 **뒷받침**

훅은 매칭되는 행동마다 실행되므로 **빠르고 변경된 파일로 범위가 좁아야** 한다. 전체 테스트 같은 무거운 검사는 커밋이나 PR 단계로 보낸다. 그리고 **사람에게 승인을 묻는 훅은 빌드 단계에 두지 않는다.** 병렬로 도는 모든 세션의 임계 경로에 사람을 올려놓는 꼴이 된다.

### 병렬 세션과 서브에이전트

둘은 다른 물건이다.

- **병렬 세션**은 각자 Git worktree를 가진 별개의 Claude Code 인스턴스다. 서로를 모르고, 공유하는 건 조종하는 엔지니어뿐이다
- **서브에이전트**는 한 세션 안에서 도는 범위 제한 헬퍼다. 자기 컨텍스트 윈도와 도구 제한을 갖는다

작업을 나눌 때 기준은 **파일이 겹치는가**다. 같은 파일을 건드리는 작업은 한 세션에서 순차로 돌린다. 시작은 두세 개가 적당하고, **실질적 상한은 한 사람이 제대로 리뷰할 수 있는 스트림 수**다. 리뷰가 따라가는 동안에만 세션을 늘린다.

**활용 맥락.** 이 상한이 핵심이다. 세션을 늘리는 건 공짜지만 리뷰 용량은 아니다. 리뷰가 밀리기 시작하면 세션을 줄여야지 리뷰를 줄이면 안 된다. 그 순간 §2의 "미검토 코드가 나간다"로 돌아간다.

## 6. Test와 Deploy — 검증을 사람 앞으로 당긴다

### 피드백 루프

**Claude에게 자기 작업을 검증할 방법을 항상 준다.** 테스트든, 빌드든, 스크린샷 비교든.

- 오늘 검증에 여러 명령과 환경 지식이 필요하다면 `make test` 같은 **단일 타깃으로 감싼다.** 실패 시 non-zero로 종료해야 한다
- CLAUDE.md의 Commands 절에 **정상 출력 예시**를 함께 적는다
- 목표를 **정량적으로** 준다. "test_status.py의 모든 테스트 통과", "엔드포인트가 새 필드와 함께 200 반환"
- 버그 수정은 **실패하는 테스트를 먼저 쓴다.** 버그를 테스트로 재현시키고, 예상한 이유로 실패하는지 확인하고, 그 테스트를 커밋한다. 그 다음에야 테스트를 고치지 말고 통과시키라고 시킨다

마지막 항목에 딸린 규칙이 중요하다. **코드를 고치는 에이전트가 그 코드에 대한 검사를 약화시킬 수 있으면 안 된다.** 수정 작업 중 테스트 파일 편집을 차단하는 훅이 이 역할을 한다. 수정 전부터 존재했고 에이전트가 다시 쓸 수 없었던 테스트여야 버그가 사라졌다는 증명이 된다.

### 설정에 대한 eval

여기서 흔한 혼동이 하나 있다. 플레이북이 말하는 eval은 **제품 모델의 성능 평가가 아니라 에이전트 설정의 회귀 테스트**다.

최근 작업에서 실제 태스크 20~50개를 모아 각각 프롬프트와 합격 기준을 붙인다. 그리고 **CLAUDE.md, 스킬, 훅이 바뀔 때마다** CI에서 비대화식으로 돌린다.

```yaml
name: Agent evals
on:
  pull_request:
    paths: ['CLAUDE.md', '.claude/**']
  schedule:
    - cron: '0 2 * * *'
```

**활용 맥락.** 이 설정들은 에이전트를 조종한다. 코드가 받는 회귀 테스트를 똑같이 받아야 한다. 스킬을 고쳤는데 합격률이 떨어지면 머지 전에 리뷰된다. 그리고 **프로덕션 인시던트마다 eval을 하나씩 추가**해서 회귀 테스트로 영구 보존한다.

### REVIEW.md

PR 리뷰 정책을 **패스별로 나눠 글로 쓴다.**

```markdown
# Review instructions

## Passes
세 패스를 돌리고 각 소견에 패스를 태깅한다.
- Bugs: 로직 오류, 깨진 엣지 케이스, 미묘한 회귀
- Security: 인젝션, 인증 공백, 로그의 PII
- Compliance: spec.md, plan.md, 설계 원칙과 일치하는가

## Important의 정의
동작을 깨뜨리거나, 데이터를 유출하거나, 정책을 위반하는 소견에만 쓴다.
스타일과 네이밍은 nit이다.

## nit 상한
리뷰당 nit 최대 5개. 나머지는 개수로만 요약한다.

## 보고하지 않을 것
src/gen/ 아래 생성 파일, CI가 이미 강제하는 것.
```

**활용 맥락.** 정책이 글로 없으면 소견의 품질이 실행마다 흔들린다. `Important`와 `nit`의 경계를 정의하고 nit에 상한을 두는 건 사소해 보이지만, **이게 없으면 리뷰 결과가 노이즈가 되어 아무도 안 읽는다.**

운영에서 지킬 것 두 가지다.

- **소견이 PR을 승인하거나 차단하지 않는다.** branch protection은 여전히 코드 오너의 승인을 요구한다. 코드를 쓴 에이전트가 그것을 승인할 경로가 없어야 직무 분리가 유지된다
- **소견이 CLAUDE.md로 되먹임된다.** 리뷰가 같은 실수를 두 번째로 지적하면, 그 리뷰의 일부로 교정이 CLAUDE.md에 들어간다. 리뷰도 CLAUDE.md를 읽으므로 다음 PR부터 잡힌다

### 훅을 승인 게이트로

빌드 단계 훅은 사람 없이 허용하거나 차단했다. 훅은 **물을 수도** 있다. 특정 인물이 승인할 때까지 행동을 멈추는 것이 릴리스 게이팅에 필요한 동작이다.

```bash
#!/bin/bash
# 프로덕션 배포는 명시된 릴리스 승인이 필요하다
cmd=$(jq -r '.tool_input.command' < /dev/stdin)
if [[ "$cmd" == *"deploy"* && "$cmd" == *"production"* ]]; then
  if [ -z "$RELEASE_APPROVAL" ]; then
    echo "프로덕션 배포에는 릴리스 승인이 필요합니다." >&2
    exit 2   # exit 2가 행동을 차단하고, 메시지는 Claude에게 간다
  fi
fi
exit 0
```

**차단은 스스로를 설명해야 한다.** 훅이 행동을 막으면 이유와 **승인받는 경로**가 Claude의 출력에 나타나야 한다.

팀 훅은 Git의 `.claude/settings.json`에, **협상 불가능한 훅은 플랫폼이나 IT 관리자가 소유하는 managed settings**에 둔다. 개인 엔지니어가 끌 수 없는 자리다.

규제 환경용 managed settings에서 알아둘 키는 이것들이다.

| 키 | 통제하는 것 |
|---|---|
| `permissions.deny` / `allow` | 비밀 파일 읽기 차단, 안전한 내부 루프는 사전 승인해 프롬프트 피로 방지 |
| `disableBypassPermissionsMode`, `allowManagedPermissionRulesOnly` | 엔지니어·프로젝트 파일·CLI 플래그 어느 것도 규칙을 넓힐 수 없게 함 |
| `sandbox` | 권한이 못 잡는 것을 잡는다. 도구 레벨 `WebFetch` 거부는 셸 명령의 네트워크 접근을 막지 못한다 |
| `sandbox.credentials` | 샌드박스 셸이 기본적으로 읽을 수 있는 `~/.ssh`, `~/.aws/credentials`를 거부하고 지정 환경변수를 제거 |
| `allowManagedHooksOnly` | managed settings에 정의된 훅만 실행. 프로젝트 훅은 차단 |
| `disableSideloadFlags`, `strictKnownMarketplaces` | 스킬·에이전트·훅·MCP가 승인된 마켓플레이스를 통해서만 들어오게 함 |
| `allowManagedMcpServersOnly` | 에이전트의 도구 표면을 플랫폼 팀 소유의 allowlist로 |
| `requiredMinimumVersion` | 조직이 실제로 평가한 버전 미만에서는 시작 거부 |

**활용 맥락.** `sandbox`와 `permissions`의 관계가 특히 중요하다. 둘은 **같은 목표를 다른 계층에서 강제**한다. 도구 레벨에서 `WebFetch`를 막아도 셸 명령은 네트워크에 나갈 수 있다. OS 레벨 도메인 allowlist가 있어야 이그레스가 실제로 차단된다. `failIfUnavailable`과 `allowUnsandboxedCommands: false`는 샌드박스를 **전제 조건**으로 만든다. 초기화에 실패하면 Claude Code가 아예 시작하지 않는다.

### CI/CD

순서가 정해져 있다. **읽기 전용 판단 작업부터** 시작한다.

```yaml
- name: Triage failed build
  if: failure()
  run: >
    claude -p "out/build.log의 빌드 로그를 읽어라. 가장 유력한 원인을 찾고,
    이 실패가 flaky인지 진짜인지 판정하고, PR 스레드에 올릴 세 줄 요약을 써라."
    >> triage.md
```

그 다음 기존 게이트 뒤에 쓰기 작업을 붙인다. 린트 수정, 생성 문서 갱신, 리뷰 코멘트 대응 같은 것들이다. **에이전트가 쓴 것은 전부 branch protection을 통과하는 PR로 도착하고, main으로 가는 직행로가 없다.**

자율성은 **환경별로 계층화**한다. 개발 환경에서는 에이전트가 자유롭게 배포한다. 프로덕션에서는 에이전트가 릴리스를 준비하고 릴리스 매니저가 승인하며, 훅이 그 게이트를 강제한다. 스테이징이 그 중간이다.

**롤백은 파이프라인에서 가장 많이 연습된 경로여야 한다.** 에이전트가 실행할 수 있는 단일 명령이고, 스테이징에서 정기적으로 연습된다. §9의 루프가 이 롤백을 호출하므로 미리 증명되어 있어야 한다.

## 7. Maintain — 루프를 닫는다

앞의 모든 단계는 사람이 시작해야 한다. Stage 6은 **사람 없이 시작되는** 것을 다룬다.

절차는 이렇다.

1. 안정적인 롤링 베이스라인을 가진 지표 하나를 고른다. CI 테스트 실패율, 배포 후 5xx율, PR 사이클 타임 같은 것
2. 탐지 스크립트를 쓴다. 롤링 윈도의 평균과 표준편차에 Western Electric 같은 규칙을 얹어 스파이크뿐 아니라 **느린 드리프트**도 잡는다
3. 대응 계층을 버전 관리된 설정으로 정의한다

```yaml
metric: ci_test_failure_rate
baseline: rolling_30d
rules: western_electric
tiers:
  1sigma: { action: log }
  2sigma: { action: diagnose,
            tools: "Read,Grep,Bash(gh run view *)" }
  3sigma: { action: propose,
            routes: [pull_request, runbook:rollback-deploy] }
```

**활용 맥락.** 여기서 놓치기 쉬운 설계 결정이 하나 있다. **탐지는 전적으로 결정적이고 모델이 개입하지 않는다.** 스크립트는 버전 관리되고 유닛 테스트를 받는다. 모델은 밴드를 넘은 뒤에야, 그것도 계층이 허용하는 범위에서만 들어온다. 1σ는 로그만, 2σ는 읽기 전용 진단, 3σ에서야 행동하되 **리뷰 게이트로 가는 PR을 열거나 사전 승인된 런북을 실행하는 경로로만** 가능하다.

에이전트는 진단 결과를 **Stage 1 형식의 `intent.md`로 쓴다.** 이상 징후와 증거, 제안하는 결과, 영향받는 시스템, 열린 질문. 거기서부터는 다른 모든 작업과 같은 파이프라인을 탄다. **루프가 닫힌다.**

사람은 큐를 **triage**한다. 지금 고칠지, 일정을 잡을지, 기각할지. 기각은 밴드를 튜닝해 노이즈를 줄인다. 수정이 배포되면 그 인시던트에 대한 eval을 추가한다.

## 8. 실무에서 부딪히는 지점

원문이 명시하거나 강하게 암시하는 함정들이다.

**CI가 없으면 절반이 잠긴다.** 연속 eval, PR 리뷰 루프, CI/CD 통합, 루프 자동화가 전부 CI를 전제 조건으로 명시한다. 비용이나 정책 때문에 CI를 미루고 있다면, **그 결정이 플레이북의 어느 부분을 잠그는지**를 비용 논의에 함께 올려야 한다.

**branch protection이 없으면 거버넌스 서사가 무너진다.** 플레이 10과 12는 "에이전트가 쓴 것은 전부 PR로 도착한다"를 전제한다. main에 보호가 없으면 이 전제가 거짓이 되고, 그 위에 쌓은 통제가 전부 명목이 된다. 비용이 0이므로 **가장 먼저 할 일**이다.

**CLAUDE.md가 매뉴얼로 자란다.** "한 페이지 아래"는 지키기 어렵고, 대부분의 팀이 실패한다. 증상은 세션 시작 컨텍스트가 무거워지고 낡은 규칙이 방치되는 것이다. 해법은 분량을 줄이는 게 아니라 **조건부 절차를 스킬로 내리는 것**이다.

**스킬을 통제로 착각한다.** 스킬은 조언적이다. "정책을 스킬로 썼으니 지켜진다"는 감사에서 통하지 않는다. 항상 성립해야 하는 정책에는 훅이나 PR에서 재검사하는 리뷰 패스가 뒤에 있어야 한다.

**승인 훅을 빌드 단계에 두면 병렬성이 죽는다.** 사람에게 묻는 훅은 배포 게이트에 둔다. 빌드 중 승인 프롬프트는 병렬로 도는 모든 세션의 임계 경로에 사람을 올려놓는다.

**세션 수를 리뷰 용량보다 앞세운다.** 병렬 세션의 실질적 상한은 한 사람이 제대로 리뷰할 수 있는 스트림 수다. 이걸 넘기면 도입 효과가 아니라 **미검토 코드**를 생산한 것이다.

**기존 테스트가 에이전트 설정까지 지켜준다고 믿는다.** 애플리케이션 테스트는 코드가 맞는지 보고, 설정 eval은 CLAUDE.md·스킬·훅을 바꾼 뒤에도 에이전트가 같은 수준으로 일하는지를 본다. 둘은 다른 것을 지킨다. ML 제품을 만드는 팀이 특히 헷갈리는데, 모델 성능 평가 스위트가 이미 있으니 설정 eval도 있다고 착각하기 쉽다.

## 9. 무엇부터 할 것인가

플레이는 모듈이고 각자 전제가 다르다. 비용과 전제 조건 순으로 정렬하면 이렇다.

| 순서 | 할 일 | 전제 조건 | 비용 |
|---|---|---|---|
| 1 | branch protection, 코드 오너 승인 필수 | 없음 | 0 |
| 2 | `CLAUDE.md` (`/init` 후 한 페이지로 축소) | 없음 | 낮음 |
| 3 | 피드백 루프 (단일 검증 명령 + 정량 목표) | 없음 | 낮음 |
| 4 | plan mode를 기본 시작점으로, `plan.md` 커밋 | 2 | 낮음 |
| 5 | `REVIEW.md` 작성 | 2 | 낮음 |
| 6 | 보호 경로·테스트 파일 편집 차단 훅 | 없음 | 중간 |
| 7 | 스킬로 정책 인코딩 | 없음 | 중간 |
| 8 | `intent.md` / `spec.md` 도입 | 공유 저장소, 템플릿 | 중간 |
| 9 | PR 리뷰 루프 | CI, 2, 5, 7 | 높음 |
| 10 | 설정 eval | CI, 2, 3 | 높음 |
| 11 | 승인 게이트 훅, managed settings | 승인 목록 | 높음 |
| 12 | 컨트롤 밴드 감시와 루프 자동화 | 8, 9, 11, 롤백 경로 | 가장 높음 |

### 측정 지표

각 플레이는 선행 지표와 후행 지표를 함께 정의한다. 몇 가지만 옮긴다.

| 플레이 | 선행 지표 | 후행 지표 |
|---|---|---|
| intent.md | 첫 대화에서 커밋까지 걸린 시간. 수 주에서 수 시간으로 | 제품 오너가 Design으로 승인한 비율 |
| plan mode | 첫 구현 패스에서 머지된 변경의 비율 | 변경당 재작업 횟수, diff가 `plan.md`와 일치하는 빈도 |
| CLAUDE.md | CLAUDE.md가 잡았어야 할 실수의 재발 빈도 | 신규 팀원의 첫 머지 PR까지 걸린 시간 |
| 스킬 | 정책 변경 승인에서 스킬 머지까지 걸린 시간 | 그 정책을 인용하는 리뷰 소견 수. 0에 수렴해야 정상 |
| 피드백 루프 | 에이전트 작성 변경의 CI 첫 통과율 | PR당 리뷰 시간, 변경 실패율 |
| PR 리뷰 | 첫 리뷰까지 걸린 시간. 분 단위로 떨어져야 함 | 머지 전에 잡힌 결함 대 프로덕션까지 샌 결함 |
| 루프 자동화 | 밴드 위반에서 `intent.md`가 큐에 오르기까지 | 소견이 머지된 수정이 된 비율, 동종 인시던트 재발률 |

**활용 맥락.** 스킬의 후행 지표가 특히 쓸모 있다. **그 정책을 인용하는 리뷰 소견이 0으로 안 내려가면** 스킬이 발동하지 않거나 본문이 공식 정책에서 드리프트한 것이다. 지표가 진단으로 바로 이어진다.
